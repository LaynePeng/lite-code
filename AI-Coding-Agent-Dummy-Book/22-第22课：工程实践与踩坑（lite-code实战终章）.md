到这里，`lite-code` 的架构已经完整：内核、工具、安全、Web UI、Electron 外壳、打包发布。但一个项目从"功能齐全"到"可靠可用"之间，还隔着无数真实使用中暴露出来的工程问题。本课作为全套课程的终章，复盘 `lite-code` 开发过程中**真实踩过的五个坑**——每一个都来自实际故障，而不是假设。它们没有一个是"新功能"，全部是**对已有设计的修正**，这正是工程实践的本质。

#### 1. 模型空响应：沉默的失败

**现象**：任务执行到一半，Agent 调完工具，然后……什么都没发生。没有回答、没有报错，任务以"正常"状态结束。用户看到的是工具卡片跑完了，最后一条消息永远停在工具结果上。

**根因**：某些模型（尤其是长任务的后期或被截断的上下文中）会返回**既无 content 也无 tool_calls 的空响应**。AgentLoop 的循环逻辑是"有 tool_calls 继续循环、有 content 结束任务"，空响应恰好落入夹缝——被当成正常返回处理，循环带着一个空 assistant 消息继续，或者直接安静收尾。

**修复**：空响应显式识别 + 有限重试：

```python
# core/agent_loop.py（核心）
current_step = 0
empty_reply_retries = 0
while current_step < self.max_steps:
    ...
    content, tool_calls, usage = ...

    if not content and not tool_calls:
        empty_reply_retries += 1
        if empty_reply_retries <= 2:
            messages.append(Message(
                role="user",
                content="模型返回了空响应。请继续当前任务，并明确给出下一步工具调用或最终结果。",
            ))
            continue                      # 注入提示后重试
        self.state.status = AgentStatus.FAILED_MAX_TURNS
        return await self._finish(
            "[LLM Error]: 模型连续返回空响应，任务已终止。",
            messages, stats, store_snapshot,
        )
    empty_reply_retries = 0               # 正常响应则清零计数
```

三个要点：① 重试不是重新发起同样的请求，而是**追加一条 user 消息把模型"摇醒"**——上下文里显式出现了失败说明，模型有信息自我纠正；② 重试上限 2 次，连续失败说明问题不在运气（可能是上下文已损坏或供应商故障），继续重试只会烧 Token；③ 终止时写入**明确的错误消息**并置 `FAILED_MAX_TURNS`，前端和落盘历史都能看到失败原因——这是第 2 课"输出截断落盘句柄"原则的回响：**失败也要可观测**。

#### 2. max_steps：默认值与配置迁移

**现象**：复杂任务（比如"把教程从 19 课重构为 22 课"）频繁以"超出最大步骤限制"终止。排查发现 `max_steps` 默认值是 25——对演示项目够用，对真实多文件重构远远不够：读目录树、逐个读文件、逐个改文件、跑测试，25 步只够开工。

**修复分两层**。第一层简单：默认值 25 → 100：

```python
# app.py
DEFAULT_CONFIG: Dict[str, Any] = {
    "max_steps": 100,     # 原 25
    ...
}
```

第二层才是坑：**老用户的配置文件里已经存了 `max_steps: 25`**。`_load_config` 用磁盘配置覆盖默认值，升级后老配置里的 25 会把新默认值 100 又压回去——用户升级了版本，行为却没变，还以为是 bug。于是出现了这个看似 hack 的迁移逻辑：

```python
# app.py（核心）
loaded = json.load(f)
self.config.update({k: v for k, v in loaded.items() if v is not None})
if self.config.get("max_steps") == 25:
    self.config["max_steps"] = 100        # 迁移老配置中的旧默认值
```

这个写法有理论缺陷：如果某用户**刻意**把 max_steps 调回 25，升级时会被误迁移。权衡后仍然接受——刻意调 25 的场景几乎不存在，而"升级后旧默认值赖着不走"影响所有老用户。**配置迁移的通用法则：旧默认值是"未配置"的化石，新版本要主动识别并清理它**。更严谨的做法是配置文件里只存用户显式修改过的键（区分"默认值快照"与"用户意图"），这是留给你迭代的方向。

#### 3. 会话 ID 碰撞：毫秒时间戳不够用

**现象**：快速连续点两次"新建会话"，偶发第二个会话**覆盖**第一个——会话历史张冠李戴。

**根因**：会话 ID 用毫秒时间戳生成（`session_{int(time.time()*1000)}`）。看起来精度很高，但注意两个事实：① 同一毫秒内完全可能连续两次创建（点击、脚本、前端重试）；② ID 直接用作落盘文件名，碰撞不是"概率降低"而是"后者覆盖前者"。

```python
# 错误示例
import time as _time
session_id = f"session_{int(_time.time() * 1000)}"   # 同毫秒碰撞 → 覆盖
```

**修复**：换用 UUID v4：

```python
# server/app.py（核心）
# 毫秒时间戳在快速连续创建会话时会碰撞，导致新会话覆盖旧会话。
session_id = f"session_{uuid.uuid4().hex}"
```

122 位随机性，碰撞概率在工程上为零。这个坑的教训是：**时间戳只保证"大致递增"，不保证唯一**；它适合排序、不适合做主键。任何"文件名 = ID"的设计都要在第一时间检查生成器的唯一性保证。

#### 4. "没有项目"是一等状态

**现象**：早期版本里，`AgentApp` 构造时 `workspace` 缺省取 `os.getcwd()`。桌面应用从 Finder 启动时 cwd 是 `/`，用户还没打开任何项目，Agent 却认为工作区是根目录——文件树列出整个磁盘，`execute_command` 在 `/` 下执行，灾难性的静默错误。

**修复**：让"没有项目"成为显式状态：

```python
# app.py（核心）
# Desktop application starts without a project. Keep this as an explicit
# state instead of silently treating the application's cwd as a workspace.
self.workspace = os.path.abspath(workspace) if workspace else None
if self.workspace:
    os.makedirs(self.workspace, exist_ok=True)
```

然后在服务层统一守卫：所有依赖工作区的接口（会话、任务、文件树、文件读取）先走 `_require_workspace()`，未打开项目返回 409（第 20 课已实现）。前端收到 409 后引导用户打开项目。

设计原则：**缺省值要么是安全的，要么不存在**。`os.getcwd()` 恰恰是最不安全的缺省——它总能给出一个"看起来合理"的答案，而错误答案比异常危险得多。`None` + 显式检查把静默错误变成了显式引导。

#### 5. 强制交付要求：终结"工具跑完就沉默"

**现象**：这可能是所有 Agent 框架最常见的用户投诉：Agent 修完文件、跑完测试，然后任务结束——**没有总结**。用户只能自己翻工具卡片，确认"它到底做了什么"。

**根因**：模型（尤其中小参数量模型）在长工具链之后，倾向于在最后一个工具结果处"顺流而下"地结束任务，而不是回头写总结。这不是 bug，是概率分布的自然倾向。

**修复**：System Prompt 里的强约束。它是全局规则，排在骨架最前面、位于第 10 课的项目指令与技能索引之前：

```python
# core/system_prompt.py（核心）
FINAL_REPORT_REQUIREMENT = """### 强制交付要求（必须遵守）
任务结束前必须向用户汇报结果，不能只执行工具后停止，也不能只回复"已完成"。最终回复必须使用简洁的 Markdown，至少包含：
- **完成内容**：实际完成了什么；
- **改动文件/关键结果**：涉及哪些文件或得到什么结论（如适用）；
- **验证情况**：运行了哪些测试、构建或检查，以及结果；
- **未完成事项**：仍有问题、风险或未验证内容必须明确说明，没有则写"无"。
如果任务因失败、停止、超时或达到步骤上限而结束，也必须向用户说明当前状态、原因和后续建议。"""
```

两个实现细节：① 这段要求放在 System Prompt 的**最前面**——研究表明长上下文里首尾位置的指令遵循率最高，而"交付报告"是最高优先级约束，值得最前面这个位置（它同时被复制进编号规则第 7 条，首尾各出现一次）；② 注意最后一句：**失败也要汇报**。Agent 的失败不应该是一行 `[LLM Error]`，而应包含"当前状态、原因、后续建议"——把每次失败变成可续接的上下文。

配合第 1 节的空响应重试（重试提示里同样要求"给出最终结果"），双管齐下。

#### 6. 全课程总结与回顾

恭喜你！到这里我们完成了全套 **22 课** 的 Code Agent 深度课程，并手写出了完整的 `lite-code` 框架。

```text
+-----------------------------------------------------------------------+
|                     lite-code 全景架构                                  |
+-----------------------------------------------------------------------+
|  [模块一] ReAct 与循环 (第1-5课)                                       |
|  - LLM 流式 Tool Calling 解析 | JSON 自愈 / 死循环检测 | 输出截断      |
|  - Token 预算与策略B滑动裁剪 | 静态 System Prompt（稳定前缀） | Prompt 缓存 |
|  - Token 节省策略（多层预算 / 带外存储 / 缓存铁律）                     |
+-----------------------------------------------------------------------+

|  - Ripgrep 代码感知 | Tree-sitter AST 分析 | 沙箱隔离                 |
|  - Search-Replace / Unified Diff | 项目指令与 Skills | MCP 生态接入   |
+-----------------------------------------------------------------------+
|  [模块三] 核心架构 (第12-15课)                                         |

+-----------------------------------------------------------------------+
```

回顾整套课程的方法论主线：

- **模块一**解决"循环怎么转"：流式解析、容错、预算、缓存——Agent 的地基是可靠性而不是聪明；
- **模块二**解决"能力怎么加"：搜索、AST、沙箱、精确编辑、指令/Skills、MCP——每加一种能力，都先想清楚它的安全边界与 Token 成本；
- **模块三**解决"架构怎么活"：微内核、中间件、子 Agent、Agent 类型——扩展性来自时空解耦，而不是堆 if-else；
- **模块四**把这些理论组装成一个**可以分发给别人用的产品**，并在终章承认：真正的成熟来自踩坑与修正。

至此，你不仅掌握了 Agent Harness 框架的完整理论体系，还手握一个**可独立扩展、架构清晰、可直接运行的桌面应用**。你可以基于 `lite-code` 扩展更多专属插件（如 Git 自动化、代码审查、数据库查询等），打造属于你自己的专用 AI 开发助手！
